# 第 01 章 程序分析的地图与边界

同一段退款代码，可以引出四个不同的问题：金额会不会变成负数？重复请求会不会退两次？一次退款为什么要等三秒？改动状态字段会影响哪些调用者？它们研究的是同一个程序，却需要不同的证据。

程序分析的起点不是选择工具，而是把问题写清楚。输入有哪些，观察什么行为，什么情况算错误，允许作哪些假设？这四件事决定了后面该保留多少程序细节。

## 一段代码，几种读法

先研究一个纯计算的 Python 函数，金额以整数分表示：

```python
def refund_amount(paid, already, request):
    if request <= 0:
        return 0
    remaining = paid - already
    if request <= remaining:
        return request
    return 0
```

假定入口满足 `paid >= 0` 且 `0 <= already <= paid`。取 `paid=10000, already=3000, request=2000`，先排除非正请求，再算出剩余额度 7000，最后返回 2000。我们得到了一条真实可执行的路径。若只运行这一组输入，便不能说负数、边界值和大请求也正确。

现在不选具体输入，只按条件推理：第一条返回路径输出零；第二条返回路径同时满足 `request > 0` 和 `request <= paid-already`；最后一条仍输出零。因此在上述入口假设下，所有正常返回都满足 `0 <= result <= paid-already`。这已经是一项小型程序分析。它没有执行所有输入，而是用条件概括了它们。

但它仍未回答重复退款问题。函数只计算金额，没有记录新累计值，更没有实现持久化与并发控制。把这一函数证明正确，不能替整套支付系统作保证。分析边界越清楚，结论才越有用。

## 静态、动态与混合

静态分析从代码及其模型推导性质，不以运行目标程序获取每个分析结果为前提。类型检查、数据流分析、某些符号执行器都可以属于这一范围。动态分析则从实际执行获得轨迹、覆盖率、时间、内存访问等证据。混合方法把二者连接起来，例如由静态结构引导测试，再用运行轨迹修正分析优先级。

“符号执行”并不自动等于动态分析。符号执行可以在模型上探索程序，也可以与一次具体执行同步推进；应按证据来源和执行方式说明。Clang Static Analyzer 就将自己描述为基于符号执行的路径敏感、跨过程源码分析器，见其[官方说明](https://clang.llvm.org/docs/ClangStaticAnalyzer.html)。

| 方法 | 对退款函数的做法 | 结果的实际含义 |
| --- | --- | --- |
| 测试与动态观察 | 给定具体三元组并记录返回值 | 这些执行发生了什么 |
| 静态推理 | 沿分支传播条件，推导返回值范围 | 在模型和假设下，哪些行为可能发生 |
| 混合分析 | 找到未覆盖分支，构造输入后运行 | 模型建议的行为能否在该环境中出现 |

分析不是只有“报错”一种输出。一个工具可以返回可能调用的函数集合、变量范围、反向切片、资源状态或性能热点。这些中间事实，常常比最终告警更容易复用。

## 从优化到验证，再到工程维护

编译优化需要知道某次计算是否多余、某个值是否固定、两次内存访问是否可能指向同处。缺陷检测需要知道不良状态是否可达。维护工具则关心修改会影响哪些位置。问题不同，背后却经常复用控制流、数据依赖与抽象状态。

[Clang 的数据流分析导论](https://clang.llvm.org/docs/DataFlowAnalysisIntro.html)同时讨论了程序事实与重构用途。这提醒我们：程序分析是一组理解程序的方法，其应用范围远大于安全扫描。本书会保留优化、维护、性能和语言设计的实际位置。

历史上，抽象解释为许多静态分析提供了统一的理解方式：保留关心的信息，舍弃与问题无关的细节。Cousot 与 Cousot 的[1977 年论文](https://www.di.ens.fr/~cousot/COUSOTpapers/POPL77.shtml)是这一方向的代表。现在先记住一个直觉：为了判断退款是否为负，我们可能只需要数值范围，无需知道订单的收货地址。

## 范围怎样划定

本书从语言语义走到机器执行，因为相同写法在不同语言里可能有不同的溢出、求值和异常规则；也会进入 CPU、GPU，因为并发、同步和成本依赖执行环境。硬件细节只有在改变程序行为或分析判断时才展开，芯片电路与完整 GPU 应用开发不在主线内。

阅读一份分析结果时，可以先填一张五项说明：分析对象是什么，关心什么性质，使用什么模型，覆盖了哪些输入或路径，仍有哪些未知。无法填写这些信息的“没有问题”，很难用于决策。

例如，退款函数的当前结论可写成：“对 Python 整数上的纯计算函数，在入口金额关系成立且正常终止时，返回金额位于允许范围内；未分析持久化、并发、权限与第三方支付。”这比一个笼统的“退款安全”清晰得多。

## 沿着问题读这本书

如果目的是理解一个陌生项目，可以先读程序表示、调用图和切片，再回头补静态分析算法。如果目的是解释线上异常，可以从轨迹、动态检测和并发章节进入，但仍要回到语言语义确认观察代表什么。如果想设计分析器，则需要按主线把表示、抽象与评估连起来。

贯穿案例会故意逐层增加复杂度。退款先只讨论整数计算，再增加对象状态，然后加入网络失败和并发请求；文件处理先只画资源生命周期，再加入别名与异常；队列则逐步引入线程、异步与内存可见性。这种安排可以看清：困难来自程序增加了哪项能力，而不是把所有现实细节一次压到读者面前。

书中会明确区分手工推演、可运行教学程序与真实工具报告。推演用于暴露算法步骤；实验用于观察实现行为；真实报告用于讨论工程限制。它们都可提供知识，却不能互相冒充。阅读时可以在页边记下一个问题：“为了得出这个结论，本节舍弃了什么？”这会成为理解分析精度最稳定的线索。

## 练习与参考答案

把入口假设删掉，只保留 `paid >= 0`，上述返回值范围还成立吗？请给出一组输入，并说明究竟是代码错误还是规格不完整。

参考答案：取 `paid=100, already=120, request=10`，函数返回 0，而 `paid-already=-20`，所以 `result <= paid-already` 不成立。原范围性质依赖 `already <= paid`。这揭示入口规格缺失；若系统允许超额累计状态进入，代码需要显式处理该异常，而分析也应覆盖这一分支。
